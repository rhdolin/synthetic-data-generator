# synthetic-data-generator

Turns real cBioPortal patients into synthetic demo patients. Each patient has two parts that describe the same person and the same tests:

1. **Clinical data as FHIR**: an mCODE transaction bundle, including a structured genomics report per test, loaded to a clinical FHIR server.
2. **Genomic data as MongoDB records** (Patients, Tests, Variants, MolecConseq, BED) for the FHIR Genomics Operations server.

The pipeline runs end to end with no person in the loop. Synthetic filler (names, addresses, date shifts) comes from a generator seeded by the MRN, so reruns are repeatable.

> **Status:** one study supported (below). Decisions and open questions: [docs/design.md](docs/design.md); field-by-field mapping: [docs/mapping.md](docs/mapping.md).

## Supported studies

Only studies whose mapping has been checked and tested are supported; `synthgen run` refuses the rest. **Adding a study is preparation work, not a switch:** its clinical attributes and timeline vocabulary must be checked, the crosswalks extended (sites, histologies, metastasis sites, tumor types for CIViC, and the MTB app's terminology), its data quirks handled, and a varied set of patients built and validated.

| Study | Status | Notes |
|---|---|---|
| `luad_tcga_pan_can_atlas_2018` (Lung Adenocarcinoma, TCGA PanCancer Atlas) | Supported | 328 eligible patients (living, with clinical data) |

Run `synthgen studies` for each study's caveats. In general:
- Names, addresses, practitioners, encounters, labs, ECOG (when not in the source), allergies and report texts are **synthetic**, generated by rule; about 15% of patients are deliberately **messy** (flagged in the run report).
- Some clinical values are **rule-filled**: metastasis sites (not in TCGA or GDC) and PD-L1 (derived from tumor RNA).
- All dates are **shifted** so the tumor board falls on a chosen date; real treatment histories (2005–2013 for TCGA) can look dated (design Q15).
- **Images are real, reports are synthetic.** Pathology and imaging reports link (`DiagnosticReport.imagingStudy`) to the patient's real TCGA images in the NCI Imaging Data Commons, matched **best effort**: slides to the pathology report; radiology scans taken within 90 days of the patient's first scan (the staging workup) to the staging report, and only clearly later scans to the metastasis/progression reports. **TCGA has almost no real metastasis or progression scans**: its radiology is nearly all pre-surgery baseline imaging, so most metastasis/progression reports have no linked image (in the LUAD cohort, only TCGA-38-6178's progression report does). Imaging AI on progression scans needs another image source. The report texts are generated from the clinical record (D22), and metastasis sites are rule-filled, so a linked scan may not show what its report says, and **dates don't align**: the IDC viewer shows the scan's real (de-identified) DICOM date, e.g. 2003-01-31, while the report and `ImagingStudy.started` carry the shifted synthetic date, e.g. 2026-11-19. Each ImagingStudy's note gives both. Programmatic access: each ImagingStudy carries the DICOM study/series UIDs and an IDC DICOMweb endpoint (a viewer proxy; for bulk downloads use IDC's own tools with the UIDs).
- The genomics report's therapeutic implications come from a pinned CIViC release and a selection rule, so they can differ from what the Genomics Operations server shows.

## Usage

```bash
synthgen studies                                    # supported studies and caveats
synthgen patients --study luad_tcga_pan_can_atlas_2018 --require actionable_variant radiology
synthgen run --study luad_tcga_pan_can_atlas_2018 --patients TCGA-J2-8194 TCGA-50-5066
synthgen run --study luad_tcga_pan_can_atlas_2018 --count 20 --require actionable_variant --prefer recurrence_or_metastasis treatment_timeline fusion radiology
```

`synthgen run` harvests each patient (first use downloads the study snapshot, several GB, and the patient's GDC record), builds the FHIR bundle and Mongo records, and writes a run report. Options:

| Option | Effect |
|---|---|
| `--patients ID …` or `--count N` | which patients: by ID, or N chosen by criteria (`--require`, `--prefer`; features listed in `synthgen patients --help`) |
| `--tumor-board YYYY-MM-DD` | the tumor board date all dates are shifted to (default 2026-12-01) |
| `--validator JAR` | validate each bundle with the HL7 FHIR validator (Java 17+; e.g. `data/cache/validator_cli.jar`) |
| `--load-fhir [URL]` | load bundles to a FHIR server (no URL: `FHIR_SERVER_URL` from `.env`) |
| `--load-mongo` | load the Mongo records (`MONGO_URI`, `MONGO_DB` from `.env`; needs a user with write access); replaces each patient's records |

Patients a study can't support are refused with the reason (e.g. patients who died during follow-up). Outputs: `data/output/<study>/<patient>/` (bundle, `mongo/*.json`); report: `data/output/<study>/run-<time>/` (`summary.txt`, `patients.csv`, `log.txt`).

## Getting started

Requires Python 3.11 or later.

```bash
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install -e . --no-deps
cp .env.example .env             # then fill in server URLs (only needed for loading)
pytest
synthgen --help
```

`requirements.txt` pins exact versions; `pyproject.toml` declares the unpinned dependencies. In VS Code, the workspace settings select `.venv` automatically and activate it in new terminals.

## Data use

Source data comes from cBioPortal. Each study's terms must allow redistribution in a public demo before its patients are published (design doc Q10). Harvested data is kept out of git by default.
